# Правила написания кода

> v1.2. Действуют для всего кода репозитория. При ревью проверяются наряду
> с функциональными требованиями.

## 1. Структура и модульность

1.1. **Один модуль — одна ответственность.** Функции не собираются в одном
файле или папке «на всё». Разбивка по доменам учёта (партии, корм, яйцо,
деньги, отчёты) и слоям (см. §2).

1.2. **Файл — не больше ~300–400 строк.** Больше — повод задуматься
о выделении части в отдельный модуль. Не догма, а сигнал.

1.3. **Общие вещи — в общие модули**, а не скопированы: клиент API, работа
с датами, деньги, форматирование — по одному месту на каждый.

## 2. Разделение слоёв

2.1. **Backend: API ≠ бизнес-логика** (правило владельца, обязательное):
- `routers/` — только приём HTTP, валидация входа, вызов сервиса, статус-коды.
  Никаких расчётов и запросов к БД «на месте»;
- `services/` — бизнес-логика: правила склада, распределение общих расходов,
  расчёт метрик, создание связанных транзакций денег. Работает с сессией БД,
  вызывается из роутеров;
- `models/` — SQLAlchemy-модели; `schemas/` — Pydantic-схемы API;
- `core/` — инфраструктура (конфиг, БД, безопасность, зависимости).

2.2. **Frontend: представление ≠ логика** (правило владельца, обязательное):
- **Компоненты** — только представление: разметка + то, что касается отображения
  (состояние формы, подсветка ошибки). Бизнес-условий («можно ли закрыть партию»)
  в JSX быть не должно;
- **API-клиенты** (`src/api/`) — весь fetch и типы ответов; компоненты не делают
  fetch напрямую;
- **Хуки** (`src/hooks/`) — переиспользуемая логика состояния (например,
  `useBatches` — загрузка и кэширование партий);
- **Утилиты** (`src/lib/`) — форматирование дат, денег, весов; расчётные функции
  дублирующие бэкенд, держим по возможности на бэкенде (см. 2.4);
- **Страницы** (`src/pages/`) — композиция компонентов + подключение хуков;
- Если страница превращается в смесь разметки и логики > ~150 строк — вынести
  логику в хук, крупные куски разметки — в дочерние компоненты.

2.3. **Источник истинности для метрик — backend.** Фронтенд не пересчитывает
сохранность/FCR/прибыль самостоятельно, а берёт из API: одна формула в одном
месте (§ «Ключевые вычисляемые показатели» концепции v1.10).

2.4. **Форматирование — на фронте** (даты, кг, деньги, проценты — как показывать);
**агрегация — на бэкенде** (что считать). Не смешивать.

## 3. Язык и стиль

3.1. **Python**: PEP 8, типизация аннотациями в сигнатурах публичных функций;
имена переменных/функций — английские, **пользовательские тексты и комментарии
— русские** (язык домена — русский, «падёж», не «mortality rate» в UI).

3.2. **TypeScript**: strict mode; без `any` (исключение — пограничные парсеры
с обоснованием); имена английские, UI-тексты русские.

3.3. **Компоненты React** — функциональные; состояние — через хуки;
глобальное состояние — минимальное (авторизация), остальное локально.

## 4. Работа с БД и данными

4.1. Любое изменение схемы — только через Alembic-миграцию (никаких
`create_all` поверх живой БД).

4.2. Многотабличные операции (событие + порождённая транзакция денег) —
в одной транзакции БД, в сервисе.

4.3. Идентификаторы и справочники — по концепции v1.10: жёсткая проверка
тегов продавцов выполняется **в сервисах (API)**, UI-ограничение — только
удобство, не защита.

## 5. Ошибки и сообщения

5.1. Backend отвечает осмысленным текстом на русском («Недостаточно корма
на складе: осталось 12 кг»), а не «Internal error».

5.2. Фронт показывает ошибку рядом с формой/действием, не молчит и не
проглатывает промисы.

## 6. Тесты

6.1. Бизнес-логика в `services/` покрывается тестами (pytest): правила склада,
распределение кура-дней, формулы метрик — минимум happy path + крайние случаи.

6.2. Роутеры — дымовые тесты (статус-коды и авторизация); фронтенд — без
автотестов в первой версии, полируем потом.

## 7. Процесс

7.1. Коммиты — атомарные, сообщение на русском или английском единообразно
(выбираем английский: `feat: add batch slaughter endpoint`).

7.2. Ветки: `master` (код), `docs` (документация). **Фичи — в отдельных ветках
`feature/<имя>`, слияние в `master` через `--no-ff`** — в истории остаются
узлы слияний, и блок изменений фичи виден как единое целое (решено владельцем:
отслеживаемость изменений важнее простоты).

7.2.1. Порядок работы над фичей:
```bash
git checkout master && git pull
git checkout -b feature/slaughter-endpoint
# ... коммиты ...
git checkout master
git merge --no-ff feature/slaughter-endpoint -m "Merge feature: забой и разделка"
git push && git branch -d feature/slaughter-endpoint
```

7.3. Перед коммитом: `npm run build` (фронт) и импорт/линт бэкенда должны
проходить.

## Комментарии к трём правилам владельца

**Правило 1 (модульность)** — принято, развёрнуто в §1 с практическим
критерием размера файла (1.2) и доменной разбивкой.

**Правило 2 (API ≠ бизнес-логика)** — принято, это §2.1. Дополнение:
слою сервисов запрещено знать про HTTP (статус-коды, Request) — он
возвращает данные или доменные ошибки, роутер переводит их в HTTP-ответы.

**Правило 3 (представление ≠ логика)** — принято, это §2.2. Уточнение
«по возможности» интерпретируем так: мелкая логика отображения (visible/
disabled кнопки) живёт в компоненте — это нормально; бизнес-правила — нет.
Плюс правило 2.3 закрывает типичную дыру React-проектов — дублирование
формул на фронте.
